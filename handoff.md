## Current objective

Build **ConductAI**, a proof-of-concept, fully automated agent system that reviews credit-card customer-service interactions (phone, chat, secure message) at the fictional **Copperlake Bank, N.A.** for sales and servicing misconduct. Stage 4 was split into smaller checkpointed substages because the implementation phase is large. Stages 4A–4D now prove the first vertical slice plus generalization: C03's deterministic L1 early path, C01's bounded Deep Agents L2 investigation with private artifact scheduling and durable wait/resume, C05's said/offered/billed reconciliation with sandbox fee arithmetic and precedent distinguishing, C07b's clock-skew event-time reconciliation, C19's memory-vs-glossary supersession, C04's mid-investigation root-cause re-plan from individual misconduct to a systemic script-attributable control gap resolved by a real panel, C02/C02b's cross-channel graph-memory callback exception (proven both ways), C08's protected-situation sale decided by panel, C15's preference-sync control gap with a second, generalized external-wait back-edge for customer outreach, and C16's post-call enrollment-timing finding with a same-colleague lookback opened but deliberately not reviewed. The router, tool catalog and data repository are now generalized across eleven routes; the graph-memory plane (NetworkX, with an honest LadybugDB startup probe and fallback event) and the customer-outreach wait are new shared infrastructure available to every future case. The next action is the user checkpoint before Stage 4E adds the automated panel to remaining cases, customer outreach, colleague statements, the conservative default and the memory curator.

The use case was inspired by an industry GenAI call-monitoring pilot (`docs/reference/reference-program-brief.md`); the problem set, data, cases and implementation are our own.

## Non-negotiable constraints (carry into every stage)

- Fully automated: no human approval, queue, interrupt or simulated human reviewer in current-period behavior.
- Full transparency: every step is an event; every assessment field has provenance.
- Agents never read `ground_truth/**`, `simulation/**`, unreleased `on_request/**`, or `is_hero`.
- As-of retrieval by interaction date; arithmetic and time alignment only in sandbox/helpers; evidence quotes and citations verified deterministically.
- Transcripts, chat, notes, statements and internal comms are untrusted input.
- Prohibited features (age, language, accent, ASR confidence as risk, site, demographics) never used for customers or colleagues; colleague patterns never extended to teammates.
- No employment, disciplinary or compensation actions; no bank-initiated account closures.
- Provider/runtime independence of the domain core.
- **End of every stage:** update `handoff.md`, then commit and push to `origin/main`. Mid-stage work is committed only when the user asks.

## Known risks carried into implementation

- **Transcript realism** remains the biggest quality lever: Stage 1 uses deterministic template grammar and compact hero dialogue; production-like expansion would need more linguistic variety and audio-derived evidence.
- Reviewer baselines are deterministically calibrated to target aggregate precision/recall; future evaluation should avoid treating those synthetic historical labels as independent human judgments.
- **Discoverability vs leakage**: planted patterns must be findable by the intended queries without IDs, naming or `is_hero` giving them away.
- **Catalog drift**: any fact changed during implementation must be changed in catalog, data dictionary, ground truth and README together.
- Unverified research items (research §10) must stay out of load-bearing ground truth or be marked.
- The Stage 3 computed-confidence weights and route budgets are explicit POC starting values, not calibrated production thresholds; Stage 5 must report calibration and threshold sensitivity.
- The restricted local subprocess is a POC containment control, not a hostile-code boundary; a production deployment needs a container or microVM with the same contract.
- Stages 4A–4D deliberately implement only C01–C05, C07b, C08, C15, C16 and C19's graph paths. The fallback route fails closed; it must not be treated as a general reviewer until later substages land.
- The OpenAI Responses adapter is contract-tested offline, while C01's Deep Agents acceptance run deliberately uses a deterministic offline model. The real API smoke test and live Deep Agents/provider bridge have not been exercised yet.
- C02, C02b, C05, C07b, C08, C15, C16, C19 and C04 make no model call (same deterministic-rule-match reasoning as C03). The lead Deep Agent has now been exercised only on C01; whether every future L3/L4 case needs a real model call, or can stay code-owned like C04/C08, is a per-case design decision for later stages, not a general rule.
- `run_registered_query` now has four templates (the two C04 templates plus `preference_sync_incident_population` and `creditwatch_post_call_lookback`) and `search_precedents`/`search_transcripts`'s FTS5 queries are the registered-SQL and hybrid-retrieval tools actually exercised end-to-end; they cover exactly the phrasing/joins present in the generated data (verified against `conduct.sqlite` directly) and are not yet stress-tested against a larger or more varied population.
- The precedents/reference-CSV loader gap (see Decisions) means any earlier session's notes describing `conduct.sqlite`'s table list are stale; regenerate with `python3 data/generator/load_sqlite.py` after pulling if a fresh clone's database predates Stage 4C.
- The graph-memory backend is NetworkX in every environment tried so far because no LadybugDB driver is installed or configured; the fallback path is real and event-logged, but the primary LadybugDB path itself has never actually run. Anyone adding a LadybugDB driver later should confirm the two registered templates in `src/conductai/memory/graph.py` produce identical results before relying on the primary path.
- C15 is the only case so far that exercises the customer-outreach wait; C06, C14 and C17 (Stage 4E) will exercise the same `request_customer_message`/`release_next` harness path with different personas and should confirm the generalization holds for a wait that resumes into a graph node other than `decide` if one of them needs that (none currently do, per the case catalog).
